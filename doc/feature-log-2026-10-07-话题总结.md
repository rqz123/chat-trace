# 新功能：话题总结（2026-10-07）

替换原来的「总结范围」页（只能计算消息数量）。用户需求：

1. 在指定会话下，按 1 天、3 天、1 周或指定时间段，把内容总结成话题；
2. 每个话题以摘要形式呈现问题、讨论、结论和开放问题；
3. 话题可能跨时间段延续（仅作讨论，见第 5 节）。

实现参考 `C:\Works\zoom-chat-kb-hub`（只读参考，未修改该项目）。

## 1. 处理流程

1. 预览（`POST /api/summaries/preview`）：显示消息数、字数、发送者数、分段数、可复用缓存的段数、当前模型和配置来源。不调用 AI。
2. 分段：按时间升序排列；相邻消息间隔超过 6 小时，或单段超过 150 条或 2 万字时切分；单条消息截断到 2000 字。
3. 逐段提取：每段调用一次 OpenAI Responses API（Pydantic 结构化输出，`store=False`），最多 4 段并发。输入包含消息 id、时间、发送者（自己发的显示为“我”）和正文。
4. 校验来源：模型返回的 `source_message_ids` 只保留本段输入中存在的 id；没有有效来源的话题直接丢弃。
5. 跨段合并：段数大于 1 时再调用一次模型，把跨段的同一话题合并（例如上午提出、下午得出结论），并给出整段时间的概览。服务端校验 `member_ids`：越界或重复使用的 id 会被忽略；模型漏掉的话题原样保留，不会丢失。合并后的来源是各成员来源的并集。
6. 保存：话题按首条消息时间排序，写入 `summary_topics` 和 `summary_topic_sources`。

每个话题的字段：`title`、`question`、`discussion[]`、`conclusions[]`、`open_questions[]`、`status`、`participants[]`，以及来源消息。`status` 的取值：`resolved`（已有结论）、`ongoing`（仍在进行）、`inconclusive`（无明确结论）。

## 2. 与 zoom-chat-kb-hub 的异同

| 方面 | zoom-chat-kb-hub | 聊迹 |
|---|---|---|
| 触发方式 | 后台持续提取“最近交流主题” | 用户按会话和时间范围按需生成 |
| 分段 | 按 Zoom thread，间隔 6 小时，每段 60 条或 2.4 万字 | 微信没有 thread，按间隔 6 小时，每段 150 条或 2 万字 |
| 跨段处理 | 关键词候选 + AI 判断是否为“同一问题”（置信度 ≥ 0.85）后合并 | 同一次总结内用一次合并调用处理；跨不同总结不做合并（见第 5 节） |
| 共同点 | OpenAI 配置读取顺序、模型档位（低/中/高）、`store=False`、提示词把聊天内容声明为不可信数据、按输入 hash 去重、服务端校验来源 id | 同左 |

## 3. 配置与数据边界

- 配置读取顺序与 zoom 项目相同：环境变量 `OPENAI_API_KEY` → `OPENAI_CONFIG_FILE` → `<数据目录>/openai_config.json` → `C:\Works\access-redmine\openai_config.json`（可用 `CHATTRACE_OPENAI_FALLBACK_CONFIG` 修改）。
- 模型档位保存在 `app_meta.ai_model_tier`：`low` = `gpt-5-mini`，`mid` = `gpt-5.6-luna`（默认），`high` = `gpt-5.6-terra`。
- 只发送所选会话在所选时间段内的文字消息，页面在生成前会明确说明。
- API key 不写入数据库，也不出现在页面、接口响应或日志中（有测试覆盖）。日志只记录总结 id、消息数、话题数和 token 数。
- 单次总结上限 6000 条消息，超过时要求缩短时间段。

## 4. 存储（schema v3）

- `topic_summaries`：一次总结的会话、范围、范围标签、状态、模型、提示词版本、消息数、分段数和进度、概览、token 用量和错误信息。
- `summary_topics` 和 `summary_topic_sources`：话题内容，以及话题与来源消息的关联。
- `ai_window_cache`：以“提示词版本 + 模型 + 分段内容”的 hash 为键缓存每段的提取结果。重复生成或范围有重叠时，未变化的分段不会再调用 API。
- 迁移 v3 会删除 v1 遗留的空 `summaries` 表（只在表为空时删除）。
- 当范围内现有消息数与生成时不同（例如后来同步了新消息，或修复后的旧消息被更新），总结会标记为“有新消息，可重新生成”。
- 启动时，状态为 `queued`/`running` 的残留总结会被标记为 `interrupted`。

## 5. 话题延续（需求第 3 点）的处理

本版**不跨不同总结关联话题**，但每个话题都保存了状态（已有结论 / 仍在进行 / 无明确结论）和开放问题。在同一次总结内，跨段的同一话题会被合并（演示中“上午提出 bug、下午确认修复”合并成了一个话题）。

后续可选方案（未实现）：

- **B. 带上次未结束的话题**：生成新的时间段时，把同一会话上一份总结中状态为“仍在进行”的话题作为上下文传给模型，让它标注每个话题是“延续”还是“新话题”。这种方式轻量，适合连续的时间段。
- **C. 话题库**：参照 zoom 项目，在跨总结范围内做候选匹配、AI 判断和合并，并保留合并记录。zoom 项目的数据可供参考：56 个话题中有 31 个后来被合并。重叠的时间段和匹配误差需要额外处理。

## 6. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET / PUT | `/api/ai/settings` | 读取或修改模型档位；返回值不含 key |
| POST | `/api/summaries/preview` | `{conversation_id, start_at, end_at}` |
| POST | `/api/summaries` | 再加 `range_label`；在后台生成，立即返回总结记录 |
| GET | `/api/summaries?conversation_id=` | 历史列表，包含话题数和 `stale` 标记 |
| GET | `/api/summaries/{id}` | 完整总结，包含话题；进行中时包含进度 |
| POST | `/api/summaries/{id}/cancel` | 取消 |
| DELETE | `/api/summaries/{id}` | 删除总结（原始消息不受影响） |
| GET | `/api/summary-topics/{id}/messages` | 话题的来源消息（原文） |

原接口 `POST /api/summaries/source` 已移除。

## 10. 补充：按生成时间保存和回顾（2026-10-07）

用户需求：生成的话题要一直保存，按生成时间回顾，直到用户自己删除；微信原始聊天不能删除。

- **保存**：本来就是永久保存的。代码中没有任何自动清理或过期删除；启动时只会把未完成的总结标记为“已中断”，不会删除。“按此范围重新生成”会**新增**一份总结，旧的保留。
- **删除边界**（已核对代码）：
  - 全项目没有 `DELETE FROM messages` 或 `DELETE FROM conversations`；
  - 删除总结只会级联删除 `summary_topics` 和 `summary_topic_sources`（话题与消息的关联行）；
  - `summary_topic_sources.message_id` 上的 `ON DELETE CASCADE` 方向是“消息被删时删关联”，反过来不成立；
  - 微信原始数据库对聊迹始终只读。

  新增测试 `test_summaries_are_kept_and_delete_never_touches_messages`：删除一份总结后，消息数、FTS 索引、另一份总结及其原文引用都保持不变；重新生成会新增记录；列表按生成时间倒序。
- **回顾界面**：
  - 历史列表按**生成日期**分组（今天 / 昨天 / 具体日期），每条显示“HH:MM 生成”和总结覆盖的时间范围；
  - 新增“本会话 / 全部会话”切换，“全部会话”跨会话按生成时间排列，并显示会话名；
  - 总结详情的头部也显示生成时间；
  - 删除确认框明确写明：只删除这份总结，微信中的聊天记录和聊迹已归档的消息都不会被删除。
- **修复**：在“全部会话”中打开其他会话的总结后，“按此范围重新生成”原本会用当前下拉框里的会话，现在改为使用该总结自己的会话。
- 列表接口默认返回最近 200 份（最多 500 份）。
- 测试：50 个，全部通过。已重启服务（这次没有 schema 变更），重启后用户已有的 1 份总结仍在。

## 11. 补充：历史列表默认显示全部会话（2026-10-07）

用户反馈：生成过两次总结，但左侧只显示一份。

- **原因**：
  1. 两份总结分别属于两个会话（#16 和 #7），而历史列表只显示下拉框中当前选中会话的总结；
  2. 用户浏览器使用了缓存的旧版页面文件。静态文件响应没有 `Cache-Control`，浏览器按启发式规则缓存，所以第 10 节的“本会话 / 全部会话”切换和生成时间都没有显示出来。
- **修改**：
  - 历史列表默认显示**全部会话**，按生成时间倒序排列；“本会话”保留为筛选项。每条固定显示三行：会话名、范围、生成时间（加状态和话题数）。
  - 点开历史中的某份总结时，顶部的会话下拉框同步切换到该会话。在“全部会话”模式下切换下拉框，不会关闭当前查看的总结。
  - `/` 和 `/static/*` 的响应加上 `Cache-Control: no-cache`。浏览器每次都会用 ETag 校验，文件没变时只返回 304，开销很小，更新后刷新即可看到新版本。新增测试 `test_ui_files_are_revalidated`。
- 测试：51 个，全部通过。已重启服务，2 份总结都在，静态文件已带 no-cache。
