# 微信聊天本地归档与总结工具 PRD

| 项目 | 内容 |
|---|---|
| 文档版本 | v1.0 |
| 产品形态 | Windows 本地服务 + Web UI |
| 面向用户 | 使用 Windows 微信个人版、希望整理本人本机聊天记录的用户 |
| 核心原则 | 用户主动、会话白名单、只读微信、数据本地保存、同步可恢复、结果可追溯 |
| 首期范围 | 单机、单微信账号、纯文字消息、手动同步、本地查询、指定日期总结 |

## 1. 产品概述

### 1.1 背景

大量工作沟通发生在个人微信中，但微信缺少面向个人聊天记录的官方查询、结构化归档和总结接口。用户需要在不修改微信数据、不自动发送消息的前提下，将本人电脑上已经同步的指定会话保存到本地数据库，并进行检索和阶段性总结。

### 1.2 产品定义

本产品是一个运行在用户 Windows 电脑上的本地工具，通过 Web UI 让用户：

1. 检测本机正在运行的微信及本地数据目录；
2. 查看本机已存在的会话列表；
3. 手动选择需要归档的会话；
4. 主动执行历史同步或增量同步；
5. 将选中会话的文字消息保存到产品自己的本地数据库；
6. 按会话、关键词和日期范围查询消息；
7. 对指定会话和日期范围生成总结，并保存总结记录。

产品不连接微信服务器，不修改微信数据库，不向微信发送消息，也不自动扩大同步范围。

## 2. 产品目标与成功指标

### 2.1 产品目标

- 用户可以明确控制哪些会话进入本地归档。
- 首次同步能够导入本机已有的历史文字消息。
- 后续同步只处理新增或发生变化的消息，并避免重复。
- 用户可以快速检索已归档聊天记录。
- 用户可以指定日期范围生成有来源依据的聊天总结。
- 微信读取失败时，不损坏微信数据和产品中已经归档的数据。

### 2.2 首期成功指标

| 指标 | 目标 |
|---|---|
| 数据库密钥验证 | 当前支持版本下，所有目标数据库均通过 HMAC 校验后才允许读取 |
| 历史同步完整性 | 对选定时间范围内、源数据库可见的文字消息，成功导入率 ≥ 99.9% |
| 重复率 | 同一来源消息重复入库率为 0 |
| 增量同步 | 再次同步时能够导入新增消息，不重复导入旧消息 |
| 会话隔离 | 未被选择的会话不得写入消息归档表 |
| 查询响应 | 10 万条消息规模下，普通日期查询首屏响应 ≤ 2 秒 |
| 同步可恢复 | 同步中断后可重新执行，不产生重复数据或破坏既有数据 |
| 可追溯性 | 每次同步与总结都有时间、范围、状态和统计记录 |

## 3. 用户与核心场景

### 3.1 用户角色

首期只有一个角色：本机用户。系统默认不提供远程访问和多用户权限体系。

### 3.2 核心用户故事

- 作为用户，我希望看到本机微信的会话列表，以便选择需要归档的工作会话。
- 作为用户，我希望首次选择一个会话后同步过去一段时间或全部可见历史消息。
- 作为用户，我希望隔几天手动点击同步，只追加这几天的新消息。
- 作为用户，我希望输入关键词并限定会话和时间范围，找到相关讨论。
- 作为用户，我希望选择一个或多个会话及起止日期，生成讨论总结。
- 作为用户，我希望看到总结引用了哪些原始消息，避免模型凭空生成结论。
- 作为用户，我希望取消某个会话的后续同步，但保留已经归档的数据。
- 作为用户，我希望能够明确删除某个会话的本地归档数据。

## 4. 产品范围

### 4.1 v1 必须实现

- Windows 本地运行。
- 浏览器访问的 Web UI，默认仅监听 `127.0.0.1`。
- 自动检测一个当前登录的 Windows 微信账号。
- 读取微信本地会话列表。
- 会话白名单选择与保存。
- 历史同步、增量同步和重新扫描。
- 只归档文字消息。
- 本地 SQLite 数据库。
- 会话浏览、日期筛选、关键词查询。
- 指定会话及日期范围生成总结。
- 同步记录、错误记录和总结记录。
- 本地数据导出与删除。

### 4.2 v1 不实现

- 发送消息、自动回复、群发、加好友等写操作。
- 修改、删除或回写微信原始数据库。
- 云端拉取未同步到电脑的聊天历史。
- 手机端应用。
- 图片识别、语音转写、视频或附件正文解析。
- 微信多账号同时在线同步。
- 后台自动定时同步；首期由用户手动触发。
- 自动启动微信、判断微信自身同步完成以及自动关闭微信；该能力仅作为后续规划，v1 不实现。
- 跨电脑自动合并。
- 企业级审计、组织权限与集中管理。

### 4.3 关键产品边界

“全部历史”指当前电脑微信数据库中实际存在、且工具能够读取的历史，不代表微信服务器或手机中的完整历史。UI 必须明确展示这一说明。

## 5. 核心流程

### 5.1 首次使用

1. 用户启动本地应用。
2. 应用启动本地后端和 Web UI。
3. 系统检测微信进程、客户端版本、登录状态和数据目录。
4. 系统只读扫描数据库密钥，并进行 HMAC 验证。
5. 验证成功后加载会话目录，但不自动归档任何消息。
6. 用户勾选需要归档的会话。
7. 用户为每个会话选择历史同步范围：
   - 全部本机可见历史；
   - 从指定日期开始；
   - 最近 7/30/90 天。
8. 用户点击“开始同步”。
9. 系统展示进度、已扫描数量、已新增数量、跳过数量和错误数量。
10. 同步成功后进入归档浏览页面。

### 5.2 日常增量同步

1. 用户打开应用。
2. 首页展示上次成功同步时间和当前微信状态。
3. 用户点击“同步已选会话”。
4. 系统读取每个会话的同步游标，并扫描游标之后的消息。
5. 系统同时执行一个有限回看窗口，用于补偿迟到写入、分片变化或边界遗漏。
6. 新消息写入本地数据库；已存在消息执行幂等校验。
7. 所有消息成功提交后更新会话游标。
8. 页面展示本次同步结果。

### 5.3 查询与总结

1. 用户选择一个或多个已归档会话。
2. 用户选择开始日期和结束日期。
3. 用户可选输入关键词或参与者。
4. 系统查询本地数据库并展示命中数量和消息列表。
5. 用户点击“生成总结”。
6. 系统冻结本次总结对应的消息集合及范围。
7. 当消息过多时，系统分段总结，再合并为最终总结。
8. 总结结果展示关键结论、决策、行动项、未决问题和引用来源。
9. 用户可保存、重新生成、复制或导出总结。

### 5.4 微信临时启动与归档编排（规划项，暂不实现）

该流程用于满足“需要归档时临时运行微信，待微信将消息落到本机后完成聊迹增量归档，再按需退出微信”的场景。它不属于 v1 实现范围，当前仅记录产品与安全设计。

推荐优先采用半自动流程：

1. 用户在聊迹中主动点击“启动微信并等待同步”。
2. 系统记录操作前微信是否已经运行；只有本次由聊迹启动的微信，才具备后续自动关闭资格。
3. 系统启动微信客户端，但不代替用户登录，不绕过二维码、密码、手机确认或其他安全验证。
4. 用户完成登录后，系统监控本地微信数据库及 WAL 文件的变化情况。
5. 当数据库持续 30～60 秒没有新增写入时，系统将状态标记为“数据暂时稳定，可以归档”。该状态只是本地工程判断，不等同于微信服务器确认历史消息已经全部同步。
6. 系统对已选会话执行一次增量归档。
7. 首次归档完成后再次进行短暂稳定性检查，并执行一次补偿扫描，降低同步期间新消息或延迟写入造成遗漏的概率。
8. 归档完成后默认提示用户自行关闭微信。
9. 后续版本可提供“完成后自动关闭微信”选项，但必须默认关闭；启用后也只能尝试正常退出，禁止直接强制终止进程。

自动关闭必须同时满足：微信由本次流程启动、归档任务成功结束、数据库写入已经稳定、用户明确启用自动关闭，并且未检测到需要保留微信运行的交互状态。无法可靠判断通话、文件传输或用户正在操作时，应放弃自动关闭并提示用户处理。

桌面微信能够同步的历史范围由微信自身决定。聊迹只读取已经落入本机数据库的数据，不得将“本地暂时稳定”描述为“云端消息全部同步完成”。

## 6. 功能需求

### FR-01 本机状态检测

系统应展示：

- 微信是否运行；
- 当前微信版本；
- 是否找到数据目录；
- 当前可识别账号数量；
- 数据库密钥验证结果；
- 工具版本对当前微信版本的兼容状态；
- 微信自动更新风险提示；
- 最近一次成功同步时间。

如果微信未运行、未登录、权限不足或版本不兼容，系统不得进入消息同步，并应提供明确的错误说明。

开发、PoC 和首批使用阶段应由用户关闭微信自动更新，将客户端固定在已经完成回归验证的版本。产品不得自行修改微信安装目录、更新程序、系统服务或注册表来强制屏蔽更新；只提供操作指引和状态提醒。

关闭自动更新只是降低版本漂移风险的运行措施，不是产品兼容机制。每次同步前，系统仍必须读取微信完整版本号，与本地兼容白名单匹配。遇到未知版本时默认停止同步，并提示用户等待适配或切换回已经验证的版本。

### FR-02 会话目录

系统应从微信本地 `session.db` 和联系人数据中读取会话目录，至少展示：

- 会话名称；
- 会话类型：单聊、群聊、其他；
- 最近消息时间；
- 是否已加入归档白名单；
- 上次成功同步时间；
- 本地已归档消息数量；
- 同步状态。

支持按名称搜索、按类型筛选、批量选择和取消选择。

读取会话目录不等于同步消息；只有明确加入白名单的会话才允许写入消息归档表。

### FR-03 会话同步配置

每个会话保存独立配置：

- `enabled`：是否参与同步；
- `history_mode`：全部、指定开始日期、最近 N 天；
- `history_start_at`：历史同步起点；
- `sync_text_only`：v1 固定为 true；
- `last_successful_sync_at`；
- `sync_cursor`；
- `lookback_window`：增量同步回看窗口，默认 24 小时。

取消选择会话只停止未来同步，不自动删除已经归档的数据。删除本地归档必须是独立操作，并二次确认。

### FR-04 历史同步

历史同步必须：

- 只处理用户选中的会话；
- 支持指定开始日期；
- 按批次读取和提交，建议每批 500～2000 条；
- 支持显示进度；
- 支持用户安全停止；
- 停止或异常后可以重试；
- 每批写入均具备幂等性；
- 完成后记录实际最早和最晚消息时间。

如果微信在同步期间写入新消息，系统应以数据库及 WAL 的一致性读取结果为准；不得直接编辑源文件来获得锁。

### FR-05 增量同步

每个会话独立维护增量游标。游标至少包含：

- 最近成功同步的 `sort_seq`；
- 最近消息创建时间；
- 已扫描的数据库分片信息；
- 最近一次完整回看时间。

增量算法：

1. 从 `last_sort_seq` 之后读取候选消息；
2. 同时回看最近 24 小时或最近 500 条消息；
3. 对候选消息执行唯一键去重和内容哈希比较；
4. 在单个本地事务中写入消息并更新游标；
5. 任一步失败时回滚该批次，游标不得提前推进。

系统不得仅依赖时间戳增量，因为多条消息可能拥有相同时间，且数据库分片或 WAL 写入可能造成迟到记录。

### FR-06 消息筛选与规范化

v1 归档以下内容：

- 普通文字消息；
- 群聊中的文字消息；
- 引用消息中的可解析文字正文，可保存引用关系；
- 可选保存“撤回了一条消息”等系统文本，但必须与普通消息区分。

v1 不归档：

- 图片二进制；
- 语音二进制；
- 视频；
- 文件正文；
- 表情资源；
- 小程序完整载荷；
- 转账、红包等敏感业务载荷。

对于非文字消息，可选择完全忽略，或仅保留类型占位符。v1 默认完全忽略，避免用户误认为附件内容已归档。

### FR-07 幂等与去重

消息唯一性采用分层策略：

1. `server_id` 有效时，优先使用“账号 + server_id”；
2. `server_id` 无效时，使用“账号 + 会话 + 源分片 + local_id”；
3. 对异常数据增加内容指纹：会话、发送方、时间、消息类型和正文哈希。

数据库必须建立唯一约束。重复同步同一历史范围时，不得产生重复消息。

如果同一消息唯一键不变但正文或状态发生变化，系统应更新当前记录，并在 `message_revisions` 中记录变更前后的哈希、时间和原因。

### FR-08 本地消息浏览

消息浏览页支持：

- 单个或多个会话；
- 日期范围；
- 发送方；
- 关键词；
- 正序或倒序；
- 分页或无限滚动；
- 跳转到某一天；
- 显示消息归档时间和来源状态。

所有日期筛选在界面中使用本地时区；数据库内部统一存储 UTC 时间戳，同时保留微信原始时间值。

### FR-09 搜索

首期支持：

- 精确关键词；
- 多关键词 AND/OR；
- 会话和日期联合筛选；
- 搜索结果上下文，默认前后各 3 条消息。

SQLite 可使用 FTS5。中文搜索优先采用 trigram tokenizer；如果部署环境不支持，则回退为标准化文本上的 `LIKE` 查询，并在 UI 标注搜索能力限制。

### FR-10 聊天总结

总结请求必须指定：

- 一个或多个会话；
- 开始日期；
- 结束日期；
- 总结模板。

预置模板：

- 综合摘要；
- 决策与结论；
- 行动项；
- 项目进展；
- 问题与风险；
- 自定义提示词。

默认输出结构：

1. 核心摘要；
2. 重要事实；
3. 已达成决策；
4. 行动项（负责人、事项、截止时间；无法确定时标记“未明确”）；
5. 未决问题；
6. 风险与阻塞；
7. 时间线；
8. 原始消息引用。

每条重要结论应尽量关联消息 ID 和时间。模型不得补写原文没有的负责人、日期或决策。

### FR-11 长上下文总结

当选定消息超出模型上下文限制时：

1. 按时间顺序切分消息；
2. 为每段生成结构化中间摘要；
3. 合并中间摘要；
4. 最终总结仍保留对原始消息的引用映射；
5. 记录分段数量、模型、提示词版本和 token 统计。

### FR-12 总结记录

每次总结保存：

- 总结 ID；
- 会话范围；
- 起止时间；
- 消息数量；
- 对应消息集合摘要哈希；
- 模板及自定义要求；
- 模型提供方和模型名称；
- 生成时间；
- 总结正文；
- 引用列表；
- 状态和错误信息。

当源消息后来发生变化时，旧总结不自动覆盖，但应标记“源数据已变化，可重新生成”。

### FR-13 同步任务记录

每次同步必须形成任务记录：

- 任务类型：历史、增量、重新扫描；
- 触发方式：用户手动；
- 涉及会话；
- 开始和结束时间；
- 扫描、新增、更新、跳过和失败数量；
- 起止游标；
- 状态：等待、运行、成功、部分成功、失败、已停止；
- 错误码和安全日志。

日志中不得记录消息正文或数据库密钥。

### FR-14 数据导出与删除

支持导出：

- 查询结果为 JSON、CSV 或 Markdown；
- 总结为 Markdown；
- 全部产品数据库备份。

删除操作分为：

- 删除某条总结；
- 删除某个会话的本地归档；
- 清空全部本地归档；
- 清除本地密钥缓存。

删除本地归档不影响微信原始数据。删除会话归档或全部归档需要二次确认，并明确是否可恢复。

### FR-15 微信生命周期编排（后续规划，v1 不实现）

后续版本可评估以下能力：

- 由用户主动触发启动微信客户端；
- 展示“等待登录、微信写入中、数据暂时稳定、聊迹归档中、归档完成”等阶段状态；
- 通过数据库和 WAL 活跃度推断本地写入是否趋于稳定；
- 稳定等待时间可配置，默认建议 30～60 秒；
- 稳定后执行增量归档及一次补偿扫描；
- 可选的归档完成后正常退出微信，默认关闭；
- 如果微信在流程开始前已经运行，绝不自动关闭；
- 登录失败、写入持续活跃、归档失败或无法确认安全退出条件时，保留微信运行并提示用户。

该能力会控制微信应用的启动与退出，因此必须与“聊天数据只读”边界分开说明：聊迹仍不得修改微信数据库、注入进程或发送消息，但会在用户授权后管理微信客户端生命周期。

## 9. 系统设计约束

### 9.1 推荐组件

- 本地后端：Python + FastAPI；
- Web UI：React/Vue 任一成熟框架；
- 产品数据库：SQLite，开启 WAL；
- 微信读取适配层：独立模块，只暴露只读接口；
- 查询：SQLite 索引 + FTS5；
- 总结：统一模型适配层，支持本地模型和 OpenAI-compatible API；
- 打包：Windows 单机安装包，后端和前端随应用启动。

### 9.2 进程与文件安全

- 打开微信进程时只申请查询与读取权限；
- 禁止调用 `WriteProcessMemory`、远程线程和 DLL 注入；
- 禁止在源微信目录中创建、修改或删除文件；
- 解密工作文件只能位于产品私有目录；
- 同步完成后可按策略删除临时解密副本；
- 数据库密钥不得写日志、不得通过 Web API 返回前端；
- Web 服务默认只监听本机回环地址；
- API 使用随机会话令牌，防止其他本地网页直接调用。

### 9.3 一致性要求

- 读取源数据库时同时处理主数据库和 WAL；
- 解密和合并操作针对副本或只读数据流；
- 本地消息写入和同步游标推进必须处于同一事务；
- 同步失败不得删除已成功归档的旧数据；
- 重跑相同范围必须得到相同结果。

### 9.4 微信版本与更新管理

- 当前基线版本为 Windows 微信 `4.1.15.13`；
- 兼容性按完整四段版本号管理，不允许仅按 `4.1` 或 `4.1.15` 判断；
- 每个兼容版本记录客户端文件哈希、适配器版本和回归结果；
- 每次同步前重新检测版本；运行期间发现版本变化时立即终止新批次；
- 未验证版本采用 fail-closed：允许查询既有本地归档，但不允许读取新的微信数据；
- 适配新版本前必须重新验证密钥提取、25 个数据库 HMAC、会话读取、文字消息读取和 WAL 增量；
- 产品只提示用户关闭自动更新，不主动破坏或替换微信更新机制；
- 用户升级前应先完成一次增量同步并备份产品本地数据库。

## 10. 异常处理

| 场景 | 产品行为 |
|---|---|
| 微信未运行 | 阻止同步，提示打开并登录微信 |
| 微信版本未验证 | 标记“不兼容/待验证”，不得静默尝试写操作 |
| 进程权限不足 | 提示权限不匹配，不自动提升权限 |
| 数据目录不存在 | 提供诊断和手动选择入口 |
| 密钥提取失败 | 不进行解密，保留既有归档 |
| 部分数据库密钥失败 | 明确列出缺失库；消息核心库失败则终止任务 |
| WAL 正在变化 | 对该批次重试或重新建立稳定读取快照 |
| 同步中途关闭 | 当前事务回滚；下次从最后成功游标继续 |
| 磁盘空间不足 | 同步前检查，任务失败但不影响已有数据 |
| AI 服务失败 | 保留查询结果和总结任务，可重试，不影响消息归档 |
| 日期范围无消息 | 不调用模型，提示调整范围 |

## 11. 非功能需求

### 11.1 性能

- 10 万条文字消息历史导入应能显示持续进度；
- 同步期间 UI 不冻结；
- 写入采用批量事务；
- 查询使用覆盖索引和分页；
- 总结前先计算消息数量与字符量。

### 11.2 隐私与本地化

- 默认所有消息、索引、同步日志和总结保存在本机；
- 如果用户配置云端 AI，首次使用前必须明确提示选定消息将发送给外部服务；
- 用户可以关闭 AI，只使用同步和查询；
- 支持将产品数据目录放在用户指定的本地磁盘位置；
- 不默认启用遥测。

### 11.3 可维护性

- 微信读取适配层与产品业务层隔离；
- 通过版本适配器维护不同微信构建；
- 每个版本适配必须通过密钥 HMAC、会话读取、文字消息读取和 WAL 增量测试；
- 数据库 schema 使用迁移版本管理；
- 同步游标带算法版本，升级后可触发安全回看。

## 12. 验收标准

### AC-01 环境检测

- 能正确显示微信 4.1.15.13 的运行状态和版本。
- 数据库密钥全部通过 HMAC 校验后，状态显示为可同步。
- 将微信升级或替换为未进入兼容白名单的完整版本号后，系统允许查询既有归档，但必须阻止新的同步任务。

### AC-02 会话白名单

- 用户选择 A、B 两个会话后执行同步，本地消息表中不得出现其他会话的消息。
- 取消选择 A 后，下一次同步不再读取 A 的新消息，但旧归档仍可查询。

### AC-03 历史同步

- 指定某会话和日期起点后，只归档该起点及之后的文字消息。
- 同一历史任务重复执行两次，第二次新增数量为 0。

### AC-04 增量同步

- 首次同步后在微信中产生新文字消息，再次手动同步能够导入新消息。
- 新旧消息顺序正确，无重复。
- 同一秒内多条消息均不会遗漏。

### AC-05 中断恢复

- 历史同步进行中强制关闭应用，重启后重新同步不会重复、不会丢失已提交批次。

### AC-06 查询

- 能按会话和起止日期正确返回结果。
- 关键词结果包含前后上下文。

### AC-07 总结

- 用户可指定会话及日期范围生成总结。
- 总结页面显示实际使用的消息数量和范围。
- 主要结论可跳转到对应原始消息。
- 空范围不会调用模型。

### AC-08 只读保证

- 代码扫描和运行审计确认同步路径不调用进程写入、DLL 注入或微信 UI 发送能力。
- 同步前后微信源数据库文件内容不被产品修改。

## 14. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 微信升级改变密钥或数据库结构 | 同步立即失效 | 版本白名单、启动检测、适配层隔离、禁止静默降级 |
| 本机数据并非完整历史 | 用户误以为是云端全量 | UI 明确说明“仅本机可见数据”，显示实际最早消息时间 |
| WAL 与主库变化造成边界遗漏 | 增量不完整 | 有限回看、幂等 upsert、定期重新扫描 |
| 中文全文搜索效果不足 | 查询体验差 | FTS5 trigram；不可用时回退 LIKE，后续可换本地搜索引擎 |
| 大范围总结超出模型上下文 | 总结失败或遗漏 | 分段总结、结构化合并、保留引用映射 |
| 云端模型导致内容外发 | 隐私风险 | 默认本地；云模型显式配置和提示；按选定范围发送 |
| 解密副本和密钥泄露 | 本机数据风险 | 私有目录、权限限制、日志脱敏、可清理缓存、可选磁盘加密 |
| 非官方读取方式受平台规则限制 | 工具可能被阻断 | 只读、无注入、无网络协议仿真；仅本机本人数据；明确风险说明 |
| 将本地数据库稳定误判为云端同步完成 | 用户误以为数据完整 | UI 仅显示“本地数据暂时稳定”；执行补偿扫描；明确微信同步范围由微信决定 |
| 自动关闭打断通话、文件传输或用户操作 | 数据或使用体验受影响 | 功能默认关闭；只关闭本次由聊迹启动的微信；条件不明确时放弃关闭 |

## 15. 产品决策记录

以下决策在 v1 中固定：

1. 产品只读，不实现任何微信写操作。
2. 同步只能由用户手动触发。
3. 会话采用白名单，默认一个会话都不归档。
4. 首期只保存文字消息。
5. 历史同步与增量同步使用同一套幂等写入逻辑。
6. 本地数据库是产品事实来源；微信数据库只作为只读上游。
7. 总结必须绑定消息范围并支持引用回看。
8. 首期只支持一个当前登录账号，但数据模型预留多账号字段。
9. Web UI 仅允许本机访问。
10. 微信版本不在兼容白名单时，默认停止同步而不是冒险运行。
11. PoC 和首批使用阶段由用户关闭微信自动更新；产品本身不修改微信更新组件。
12. “启动微信—等待本地数据稳定—归档—可选退出”列为后续规划，v1 暂不实现。
13. 后续即使实现，自动退出也必须默认关闭，且不得关闭流程开始前已经运行的微信。
