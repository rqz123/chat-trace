# 新功能：启动微信并归档（2026-10-06）

对应 PRD 5.4 / FR-15“微信临时启动与归档编排”，按“半自动”方案实现第一版，入口在「运行状态」页。

## 1. 流程

| 步骤（UI） | 内部状态 | 进入下一步的条件 |
|---|---|---|
| 启动微信 | `launching` | 找到 `Weixin.exe`，程序文件版本在兼容白名单内（**启动前**检查），60 秒内出现进程 |
| 等待登录 | `waiting_login` | 微信数据库或 WAL 文件相对启动前的快照发生变化，视为已登录并开始写入（超时 10 分钟） |
| 微信写入中 | `wechat_writing` | 连续 N 秒没有文件变化（N 可选 30/45/60/90/120，默认 45；超时 20 分钟） |
| 数据暂时稳定 | `stable` | 立即进入归档 |
| 聊迹归档 | `archiving` | 执行一次普通同步任务（`SyncService.start(wait=True)`） |
| 等待补扫 | `settling` | 再连续 15 秒无写入 |
| 补偿扫描 | `rescanning` | 再执行一次同步，收录归档期间新写入的消息 |
| 归档完成 | `done` | — |

- 如果操作前微信已在运行，跳过“启动微信”和“等待登录”（UI 中以虚线表示），聊迹不会关闭它。
- 结束状态为 `done`、`failed` 或 `cancelled`。`reached` 字段记录停止时所在的步骤，供 UI 标红。
- 等待补扫期间如果用户退出了微信，流程以 `done` 结束，并说明“跳过补偿扫描”。

## 2. 设计决策

- **不关闭微信**：本版不提供自动关闭，也不提供“关闭”按钮。Windows 上没有可靠的正常退出方式：`WM_CLOSE`（`taskkill` 不带 `/F` 时发送的就是它）只会让微信最小化到托盘，而 `psutil.terminate()` 等价于强制结束，可能打断数据库写入。完成后由 UI 提示用户从托盘菜单退出。状态中保留 `launched_by_chattrace`，为以后的“可选自动关闭（默认关闭）”留出接口，届时仍需满足 PRD FR-15 的全部前置条件。
- **稳定判断**：只读取 `db_storage` 下 `.db` 和 `.db-wal` 文件的修改时间和大小，不打开微信原始库。`-shm` 文件被排除，因为读取方也会改动它。本机实测：50 个文件，每次约 14 ms，每 2 秒轮询一次。
- **只读边界**：README 的“安全边界”已重新表述为：聊天数据库始终只读；启动微信属于应用生命周期控制，只在用户点击时进行。
- **定位微信**：依次查找环境变量 `CHATTRACE_WEIXIN_EXE`、正在运行的进程、注册表（`HKCU\Software\Tencent\Weixin\InstallPath`、HKLM，以及 Uninstall\Weixin），最后是 Program Files 默认路径。只匹配 `Weixin.exe`，本机还装有旧版 WeChat 3.9（`WeChat.exe`），不会被误用。
- **启动方式**：使用 `os.startfile`，效果等同用户双击，进程与聊迹分离，聊迹退出不影响微信。
- **取消**：任意阶段都可以取消。处于归档阶段时，会同时停止对应的同步任务（为此 `SyncService.start` 新增 `on_created` 回调，在阻塞模式下也能拿到任务 id）。取消不会改变微信的运行状态。
- **状态保存**：流程状态只保存在进程内存中（包括最近 50 条事件）。两次同步仍按普通任务写入 `sync_jobs`，可在“最近同步”中查看。

## 3. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/orchestration` | 当前状态：`phase`、`reached`、`active`、`quiet_remaining`、`last_write_at`、`was_running`、`launched_by_chattrace`、两次任务 id、`message`、`events` |
| POST | `/api/orchestration/start` | `{"quiet_seconds": 15..600}`。已有流程、没有已选会话或已有同步任务时返回 400 |
| POST | `/api/orchestration/cancel` | 没有进行中的流程时返回 404 |

## 4. 改动文件

- 新增 `chattrace/orchestrator.py`。所有外部依赖（查找程序、读版本、进程检测、启动、文件快照、时钟）都通过 `Environment` 注入，`WindowsEnvironment` 是真实实现。
- `chattrace/app.py`：新增 3 个接口；`create_app` 新增 `orchestrator_env` 参数，供测试注入。
- `chattrace/sync_service.py`：`start()` 新增 `on_created` 参数。
- `chattrace/storage.py`：新增 `get_job()`。
- `chattrace/static/index.html`、`app.js`、`styles.css`：运行状态页新增“启动微信并归档”卡片，包括步骤条、倒计时、取消按钮和流程记录。
- `tests/test_orchestrator.py`（新）：11 个用例。
- `README.md`：新增使用说明，并更新安全边界。

## 5. 验证

- **自动化测试**：39 个，全部通过（原 28 个 + 新增 11 个）。新用例使用模拟时钟和模拟微信，覆盖：
  - 完整流程，并确认在最后一次写入后至少等待 N 秒才开始归档；
  - 微信已在运行时不启动、不关闭；
  - 版本不兼容时不启动；
  - 找不到程序；
  - 登录超时；
  - 持续写入超时；
  - 等待补扫期间退出微信（跳过补扫）；
  - 等待期间退出微信（失败）；
  - 等待期间取消；
  - 参数校验；
  - 通过 API 跑完整流程。
- **真实环境只读检查**（未启动微信）：在本机正确定位到 `C:\Program Files\Tencent\Weixin\Weixin.exe`，读出文件版本 4.1.15.13，快照监控 50 个文件。
- **UI**：用模拟微信运行演示服务，并用无头 Chrome 截图，确认“微信写入中”倒计时状态，以及失败时在“聊迹归档”步骤标红、显示原因，渲染都正确。演示中因为真实微信未运行，归档前检查正确拒绝，显示“无法开始归档：微信未运行”。

## 6. 待实测

需要在真实微信上走一遍完整流程，重点确认：

1. 冷启动、登录后，数据库文件的变化能否在“等待登录”阶段被正确检测到。
2. 45 秒的默认稳定时间对日常使用是否合适（历史消息较多时，微信可能分批写入）。
3. 登录前微信是否就已经写入数据库。如果是，“等待登录”会提前结束，但随后的稳定等待和归档前的检查（要求数据目录可读、能取得密钥）仍会兜底。

## 7. 后续可选

- 稳定性验证充分后，增加“归档完成后自动关闭微信”选项（默认关闭）。需要先找到可靠的正常退出方式，并满足 PRD FR-15 的全部条件：仅限由本次流程启动、任务成功、写入已稳定、用户明确启用、无通话或文件传输。
- 把流程状态持久化，使聊迹重启后能看到上一次的结果。

## 8. 上线问题：点击按钮“没有反应”（2026-10-06 18:56 已处理）

- **原因**：正在运行的聊迹服务是 13:29 启动的旧进程。Python 代码不会热加载，所以旧进程没有 `/api/orchestration` 接口，点击后返回 404。而静态文件每次请求都从磁盘读取，所以页面上已经出现了新按钮。错误只以几秒后消失的提示显示在右上角，看起来像“没有反应”。
- **前端改进**：`api()` 抛出的错误现在带上 HTTP 状态码。启动失败的原因会直接显示在卡片内（红色）；遇到 404 时提示“当前运行的聊迹服务是旧版本……请关闭并重新启动聊迹”，并停止每 3 秒一次的后台重试。已用无头 Chrome 对着旧进程截图确认。
- **处理**：经用户同意，先用 SQLite 在线备份 API 把 `data/chattrace.db` 备份到 `data/backup/chattrace-before-v2-20261006-185610.db`（完整性检查 ok，943 条消息，schema 1），然后结束旧进程，用新代码在 18765 端口重新启动（`CHATTRACE_DATA_DIR=C:\Works\chat-trace\data`；输出写入 `data/logs/server.out` 和 `server.err`）。
- **首次启动迁移结果**（真实数据目录）：schema 升到 2；943 条消息全部保留，FTS 索引 943 条；重置 1 个游标；`keys.json` 已转为 DPAPI，`.bak` 已删除；清理 56 个解密副本。修复日志中“真实数据目录尚未迁移”这一项**已完成**。
